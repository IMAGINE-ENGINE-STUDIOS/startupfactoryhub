# Imagine Engine runtime rules
- Imagine Engine flow runtime actions live in public/imagine-engine/ai.js (window.__IEX / __IEMeta) and are dispatched from the bundle's run loop; why: the minified bundle is only patched via string replacements.
- Imagine Engine per-element editing (select, Content-tab styling, drag/move across widgets) lives in public/imagine-engine/edit.js and persists to localStorage; why: widget components are minified and can't be edited in place.
- Imagine Engine account sync, media uploads, shared cart, checkout and payment setup live in public/imagine-engine/commerce.js plus the imagine-commerce edge function (user data in private storage JSON, media in a public bucket); why: no database migrations are possible on the external Supabase from here.
- Imagine Engine map widgets render a real map (same map service as the resource map) from public/imagine-engine/map.js, configured per widget section from the Content tab; why: widget bundles are minified so maps are injected alongside them.
- Imagine Engine page menu (create/rename/copy/delete/switch pages, Play page switcher) lives in public/imagine-engine/pages.js using window.__IE page helpers; why: the minified bundle only exposes hooks via string patches.
- Imagine Engine undo/redo, Record/Version Log and phone/tablet layout live in public/imagine-engine/history.js using window.__IE.raw; version restores are free; why: the minified bundle is only patched via string replacements.
- Imagine Engine gradient studio, project background (localStorage ie-bg:<pid>) and advanced Content inspector live in public/imagine-engine/design.js, mounted into #ie-design-panel / #ie-content-pro slots; why: the minified bundle is only patched via string replacements.
- Imagine Engine undo/redo snapshots include the ie-txt:/ie-sty:/ie-add:/ie-bg: localStorage keys and repaint via each edit root's __ieReload (registered in window.__IERoots); why: canvas edits are stored outside the bundle state.
- Imagine Engine solution templates, the CDN library loader (window.__IELoad) and the shared state bus (window.__IEBus) live in public/imagine-engine/blocks.js, with interactive blocks (3D, game, camera) as standalone pages in public/imagine-engine/blocks/; why: the minified bundle is only patched via string replacements.
- Imagine Engine GitHub push/pull lives in public/imagine-engine/github.js (token in sessionStorage, project exported as imagine-project.json); why: the minified bundle is only patched via string replacements.
- Imagine Engine live apps (React 19 TSX via Babel + esm.sh, or A-Frame HTML) run in public/imagine-engine/blocks/liveapp.html and read their source from Dev tab files apps/* through window.__IEFiles (ai.js); why: arbitrary AI apps need a runtime outside the minified bundle, and Dev edits must re-render the canvas.
- Imagine Engine 3D blocks include public/imagine-engine/blocks/rt3d.js (window.IE3D.attach) and take live settings/commands by postMessage {__IE3D}; the Content-tab 3D deck (edit.js) and Flow 3D steps (ai.js __IEX set3D/spawn3D/move3D/...) both talk to it; why: blocks are separate iframes, so one shared message protocol keeps sliders, Flow and AI in sync.
- Imagine Engine templates with code (cargame, webgl, game) are seeded as editable Dev files apps/*.html run by liveapp.html kind=html; the AI edits them with patchFile/updateFile and imagine-ai gets file sources plus an edit/rebuild intent; Chat mode (body.mode "chat") never emits actions; why: follow-up requests must change the running solution instead of rebuilding it or adding disconnected Flow scripts.
- Imagine Engine Canvas <-> Dev sync lives in public/imagine-engine/dev-sync.js: App.tsx is generated from the current page's sections with the data between @ie-sections markers, and valid edits to that block are written back to the canvas; why: the canvas state is bundle JSON, so a data block keeps both sides lossless.
- Imagine Engine live apps resolve relative imports (./, ../, @/, .css, .json) from Dev files as blob modules in liveapp.html and hot-reload when any imported file changes; why: there is no bundler, so multi-file apps must link inside the browser.
- Imagine Engine Flow talks to running apps through window.__IEAppBus (ai.js): ctx.broadcast/dispatchApp post {__IE_ACTION,payload} to apps' window.__IE_DISPATCH, apps call IE.emit(event) which lands in ctx.on and __IEState["app:<event>"]; an edit-intent guard drops Flow-only actions aimed at a running app and retries once with patchFile; why: Flow scripts cannot reach code inside app iframes.
- Imagine Engine 3D Studio workspace tab and the floating block toolbar (fullscreen, size presets, FPS, restart, open in Dev) live in public/imagine-engine/studio-tab.js, injected next to the bundle's mode buttons; why: the mode list is inside the minified bundle.
- Imagine Engine shops use the store template (public/imagine-engine/blocks/store.tsx, seeded as apps/Store.tsx) which checks out through commerce.js cart-cmd messages; why: there is no server, so fake /api routes can never work.
- Imagine Engine live-app SDK (IE.auth, IE.db, IE.useRoute/navigate) lives in public/imagine-engine/blocks/ie-sdk.js and saves app data through imagine-commerce action "appdb" (private storage JSON per creator/app/collection, owners edit their own records); why: real persistence without database migrations on the external Supabase.
- Imagine AI app builds: ai.js classifies each Build message (app/site/edit) and sends context.build; app builds get a no-widgets prompt, 16k output and arrive as code fences with file=<path> (root apps/<Name>.tsx|html becomes a live app, other paths Dev files), retried once if no app was produced; why: large source inside JSON strings broke parsing and the widget list pulled the AI back to widgets.
- app.html runs a pre-boot sanitizer (window.__IEFix) over ie-projects and shows a repair/clean-canvas rescue screen (with backups) if the canvas fails to render; why: damaged saved data must never white-screen the engine.
- Imagine Engine live-app visual editing: liveapp.html tags every DOM JSX element with data-ie-loc="file:line:col" (Babel plugin) and patches that exact tag's text/style in the Dev file on {ie:"liveapp-patch"}; the editor panel lives in edit.js (liveapp-select messages); why: edits must land in source so they persist, hot-reload and export.
- Imagine Engine dashboard/analytics/crm/portal requests map to the dashboard template (blocks/dashboard.tsx seeded as apps/Dashboard.tsx), never to empty pages; why: a page named Dashboard with no content was the old failure.
