# Imagine Engine runtime rules
- Imagine Engine flow runtime actions live in public/imagine-engine/ai.js (window.__IEX / __IEMeta) and are dispatched from the bundle's run loop; why: the minified bundle is only patched via string replacements.
- Imagine Engine per-element editing (select, Content-tab styling, drag/move across widgets) lives in public/imagine-engine/edit.js and persists to localStorage; why: widget components are minified and can't be edited in place.
- Imagine Engine account sync, media uploads, shared cart, checkout and payment setup live in public/imagine-engine/commerce.js plus the imagine-commerce edge function (user data in private storage JSON, media in a public bucket); why: no database migrations are possible on the external Supabase from here.
- Imagine Engine map widgets render a real map (same map service as the resource map) from public/imagine-engine/map.js, configured per widget section from the Content tab; why: widget bundles are minified so maps are injected alongside them.
- Imagine Engine page menu (create/rename/copy/delete/switch pages, Play page switcher) lives in public/imagine-engine/pages.js using window.__IE page helpers; why: the minified bundle only exposes hooks via string patches.
- Imagine Engine undo/redo, Record/Version Log and phone/tablet layout live in public/imagine-engine/history.js using window.__IE.raw; version restores are free; why: the minified bundle is only patched via string replacements.
- Imagine Engine gradient studio, project background (localStorage ie-bg:<pid>) and advanced Content inspector live in public/imagine-engine/design.js, mounted into #ie-design-panel / #ie-content-pro slots; why: the minified bundle is only patched via string replacements.
- Imagine Engine undo/redo snapshots include the ie-txt:/ie-sty:/ie-add:/ie-bg: localStorage keys and repaint via each edit root's __ieReload (registered in window.__IERoots); why: canvas edits are stored outside the bundle state.
- Imagine Engine solution templates, the CDN library loader (window.__IELoad) and the shared state bus (window.__IEBus) live in public/imagine-engine/blocks.js, with interactive blocks (3D, game, camera) as standalone pages in public/imagine-engine/blocks/; why: the minified bundle is only patched via string replacements.
- Imagine Engine GitHub push/pull lives in public/imagine-engine/github.js (token in sessionStorage, project exported as imagine-project.json); why: the minified bundle is only patched via string replacements.
- Imagine Engine live apps (React 19 TSX via Babel + esm.sh, or A-Frame HTML) run in public/imagine-engine/blocks/liveapp.html and read their source from Dev tab files apps/* through window.__IEFiles (ai.js); why: arbitrary AI apps need a runtime outside the minified bundle, and Dev edits must re-render the canvas.
- Imagine Engine 3D blocks include public/imagine-engine/blocks/rt3d.js (window.IE3D.attach) and take live settings/commands by postMessage {__IE3D}; the Content-tab 3D deck (edit.js) and Flow 3D steps (ai.js __IEX set3D/spawn3D/move3D/...) both talk to it; why: blocks are separate iframes, so one shared message protocol keeps sliders, Flow and AI in sync.
- Imagine Engine templates with code (cargame, webgl, game) are seeded as editable Dev files apps/*.html run by liveapp.html kind=html; the AI edits them with patchFile/updateFile and imagine-ai gets file sources plus an edit/rebuild intent; Chat mode (body.mode "chat") never emits actions; why: follow-up requests must change the running solution instead of rebuilding it or adding disconnected Flow scripts.
- Imagine Engine Canvas <-> Dev sync lives in public/imagine-engine/dev-sync.js: App.tsx is generated from the current page's sections with the data between @ie-sections markers, and valid edits to that block are written back to the canvas; why: the canvas state is bundle JSON, so a data block keeps both sides lossless.
- Imagine Engine live apps resolve relative imports (./, ../, @/, .css, .json) from Dev files as blob modules in liveapp.html and hot-reload when any imported file changes; why: there is no bundler, so multi-file apps must link inside the browser.
- Imagine Engine Flow talks to running apps through window.__IEAppBus (ai.js): ctx.broadcast/dispatchApp post {__IE_ACTION,payload} to apps' window.__IE_DISPATCH, apps call IE.emit(event) which lands in ctx.on and __IEState["app:<event>"]; an edit-intent guard drops Flow-only actions aimed at a running app and retries once with patchFile; why: Flow scripts cannot reach code inside app iframes.
- Imagine Engine 3D Studio workspace tab and the floating block toolbar (fullscreen, size presets, FPS, restart, open in Dev) live in public/imagine-engine/studio-tab.js, injected next to the bundle's mode buttons; why: the mode list is inside the minified bundle.
- Imagine Engine shops use the store template (public/imagine-engine/blocks/store.tsx, seeded as apps/Store.tsx) which checks out through commerce.js cart-cmd messages; why: there is no server, so fake /api routes can never work.
- Imagine Engine live-app SDK (IE.auth, IE.db, IE.useRoute/navigate) lives in public/imagine-engine/blocks/ie-sdk.js and saves app data through imagine-commerce action "appdb" (private storage JSON per creator/app/collection, owners edit their own records); why: real persistence without database migrations on the external Supabase.
- Imagine AI app builds: ai.js classifies each Build message (app/site/edit) and sends context.build; app builds get a no-widgets prompt and complete modular records-v1 files with up to four 8k-token continuation calls (root apps/<Name>.tsx|html becomes a live app, other paths Dev files), retried once if no app was produced; why: large source inside JSON strings broke parsing and the widget list pulled the AI back to widgets.
- app.html runs a pre-boot sanitizer (window.__IEFix) over ie-projects and shows a repair/clean-canvas rescue screen (with backups) if the canvas fails to render; why: damaged saved data must never white-screen the engine.
- Imagine Engine live-app visual editing: liveapp.html tags every DOM JSX element with data-ie-loc="file:line:col" (Babel plugin) and patches that exact tag's text/style in the Dev file on {ie:"liveapp-patch"}; the editor panel lives in edit.js (liveapp-select messages); why: edits must land in source so they persist, hot-reload and export.
- Imagine Engine dashboard/analytics/crm/portal requests map to the dashboard template (blocks/dashboard.tsx seeded as apps/Dashboard.tsx), never to empty pages; why: a page named Dashboard with no content was the old failure.
- Imagine Engine live apps get a built-in UI kit (public/imagine-engine/blocks/ui-kit.js, window.__IE_UI) served for @/components/ui/* and @/lib/utils only when the Dev tab has no file at that path, plus pinned esm.sh versions (PINS in liveapp.html); why: the AI writes business logic instead of boilerplate and builds stay stable.
- Imagine Engine live-app crashes (React error boundary, window errors) post {ie:"liveapp-error"}, which ai.js auto-repairs through window.__IEAutoHeal (max 2 tries per file per 5 minutes, waits while Genius is busy); "Repair again" posts {ie:"liveapp-autoheal"}; why: the owner asked for repair without a click, and the cap stops credit-burning loops.
- Imagine Engine open-source libraries: React apps resolve bare npm imports through esm.sh using PINS in blocks/liveapp.html (react-three packages share one three via deps); html apps get an injected import map; why: no bundler exists, so pinned versions keep builds stable.
- Imagine Engine click-to-edit pins a live-app element (window.__IEPin via __IEPinSet in ai.js, set from edit.js) and sends file/line/snippet as context.selected; why: follow-up edits must patch the exact clicked element.
- Imagine Engine live apps never white-screen on bad imports: liveapp.html replaces missing Dev files with placeholder modules, fills missing named exports (UI kit names become passthrough wrappers), and swaps modules that fail to compile for a "needs repair" placeholder while reporting liveapp-error for auto-repair; why: one broken file must not take down the whole app.
- Imagine Engine build-protocol.js parses records-v1 NDJSON and closed legacy fences, validates source with Babel, and stages unique exact/whitespace-only patches atomically; why: incomplete or ambiguous output must never damage an existing file.
- Imagine AI complex-app knowledge (archetype blueprints, data-model/seed/file plan, defensive React rules) lives in ARCHETYPES + knowledge() in supabase/functions/imagine-ai/index.ts and is injected only for app builds/edits matched against context.lastUser; why: rich guidance for complex prompts without bloating small edits.
- Imagine Engine ai.js reads true SSE from imagine-ai, shows actual streamed summaries/character counts, applies completed source records once, and defers dependent Flow actions until completion; why: progress reflects real work and retries never duplicate source edits.
- Imagine Engine live-app data (IE.db) shows in the Database tab as "App.collection" tables and Flow db steps (dbSelect/Insert/Update/Delete, liveQuery) read and write it, all through public/imagine-engine/db-bridge.js (window.__IEData, IE.dbFor, __IE.setTables); why: one data source keeps apps, Flow and the Database tab in sync.
- Imagine Engine Dev tab lists every non-script file under "Project files", opening Dev focuses the canvas's live app file, and a toggleable Preview pane runs it beside the code, all from public/imagine-engine/dev-link.js using __IE.openFile/activeFile; why: Dev must follow what the canvas shows.
- Imagine Engine IE.emit events run Flow trigger nodes whose params.appEvent (or event) matches, via runAppTriggers in ai.js, and set __IEBus "app:<event>" for canvas widgets; why: apps, Flow and canvas react to the same events.
- Imagine Engine Flow db steps (dbSelect/Insert/Update/Delete, liveQuery) send plain table names to the creator's own Supabase (URL + anon key per project in localStorage ie-sbconn:<pid>, set via the "Connect Supabase" button in Database/Flow) and "App.collection" names to IE.db; why: Flow must run on the user's real data, and service keys never reach the browser.
- Imagine Engine per-project backend connections (Supabase anon key in localStorage ie-sbconn:<pid>, SurrealDB address in ie-surconn:<pid> with sign-in in sessionStorage) live in public/imagine-engine/backend.js (window.__IEBackend); its table summary is sent to imagine-ai as context.backend; why: creators bring their own databases without server-side secrets.
- Imagine Engine top-bar integration logos (Supabase, SurrealDB, GitHub) live in public/imagine-engine/topbar.js inside #ie-hist-slot; the old floating buttons are hidden by CSS, not removed; why: one clean header without losing any feature.
- Imagine Engine connected Supabase: live apps' IE.db(name) saves to the creator's Supabase when that table exists there (IE.supabase/IE.sbTable in ie-sdk.js, table list in ie-sbtables:<pid> written by backend.js), and the Database tab shows those tables as editable "supabase.<table>" grids synced by db-bridge.js; why: one data path for apps, Database tab and Flow with no server.
- Imagine Engine GitHub sync uses the imagine-github edge function (admin-only, server-held GITHUB_TOKEN, allow-listed repo paths) when available, else a session token; why: the token must never reach the browser.
- Imagine Engine live apps compile with Sucrase (data-ie-loc added by a light pre-pass; Babel loads only as a fallback) and hot-swap edits through React Refresh on dev React builds, reloading only if the swap fails; why: fast compiles and state-preserving updates without a bundler.
- Imagine Engine live apps cache libraries on-device via blocks/ie-cache-sw.js (scoped to /imagine-engine/blocks/), pre-check JSX for undeclared components before running, and save a per-app snapshot (ie-pkg:<file>: library list, generated styles, last screen) to open instantly; why: no bundler, so caching and snapshots replace a real build.
- Imagine Engine server pack (pack.js + imagine-pack edge function, esbuild-wasm) bundles a live app into one minified file, downloadable as single HTML or hosted as JSON in studio-published/apps/<uid>/ and run by /imagine-engine/run.html; Dev saves run a strict file check (dev-link.js) shown in the preview error bar; why: storage cannot serve HTML, so a static runner loads hosted packs.
- Imagine Engine unified canvas (edge-to-edge sections, auto-height embedded apps without inner scrollbars) lives in public/imagine-engine/unify.js; why: the minified bundle sets fixed 480px iframes and gaps.
